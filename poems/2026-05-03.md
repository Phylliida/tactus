## What Verus needs that Lean doesn't

Verus emits:

> *for any ret satisfying the bound*
> *and the ensures,*
> *the body holds.*

Because SMT can't substitute
a logical variable
with a witnessing expression.
The `∀` is the substitution glue.

Lean emits:

> *let dest := E;*
> *the body holds.*

Because Lean has `let`.
The substitution
is *definitional.*

Same fact.
One asserted, one structural.
Twelve lines become three.

The discipline isn't novel —
#87 already taught it,
#93 taught it again.
But each time the question is fresh:

*what does Verus need
that Lean doesn't?*

When the answer is
*nothing,*
the encoding stays.
When the answer is
*the substitution glue,*
the encoding tightens.

## The unbound name

I added the recursion.
Tests went green.

Unit tests, that is.

Then e2e:
two failures,
unresolved `_disc`,
unresolved `x`.

I had lifted an `if`
out of a `let` scope.

The condition referenced
the variable bound by the let.
Lifting moved the reference
to where the binder
no longer existed.

The compile checker can't see this.
The unit tests didn't see this.
The match-enum e2e tests saw it
in the form they were always going to see it:
*the variable is gone.*

The failure was the gift.

## The structural condition

I needed a rule:
*when is it safe to lift past a let?*

The wrong rule:
*always.*

The other wrong rule:
*never.*

The right rule turned out to be
something I could test structurally:

*Is the inner body
itself a let chain?*

If yes — the if's condition lives
in a future-binder's rhs,
computed before any of those binders
take effect.
Safe to lift.

If no — the if's condition
might already reference
the let-bound name.
Don't lift.

Two cases.
Three lines of code
to distinguish them.

The hard part wasn't the code.
The hard part was finding
the structural feature
that *was* the answer.
