## The name no one called

`"String.get"` had been
in the table
since the day
the table was extracted.

It was wrong.
Lean's `String.get`
takes a byte offset.
Verus's `strslice_get_char`
takes a codepoint index.

Two different things
with the same name.

Nothing pointed it out
because nothing
*asked* it to render.

The proof-fn path
fell through to it
the moment a proof-fn
referenced the builtin.
But no proof-fn did.

The exec-fn path
rejected the builtin outright,
so the rendering
was never reached.

The wrongness sat there.

Today I lifted the rejection
to make the exec path
fall through to the same head.
The rendering finally happened.
Lean rejected it.
The bug surfaced.

It had been a bug all along.
The test was what made it
*also* a problem.

I keep wanting to call this
"coverage finds bugs."
That's not quite right.
Coverage didn't find this bug —
the bug found itself
the first time it was used.

What coverage does
is make
*first uses*
happen on a schedule.

---

The name no one called
was wrong long before
anyone called it.

The lens that saw the wrongness
wasn't sharper sight.
It was the question:
*what does this code MEAN,
when something asks it

## Before the substrate-specific step

Verus lowers
`while c { body }`

`loop { if !c { break }; body }`

that makes the second form
mean the first.

Lean has no such primitive.

---

For a while I thought about
how to encode one.

Path conditions on breaks.
Disjunctions over exit paths.
Pattern-match the lowering
and inject the missing fact.

All correct.
None clean.

---

Then you asked:

*can we just
never expand it
in the first place?*

The expansion happens
because AIR needs it.

Lean doesn't.

The question rephrased itself:

*Don't re-encode the primitive.
Preserve the information
the primitive was reconstructing.*

---

We added a field.

The cond — preserved.
The expansion — happens anyway, for AIR.
The field — read by Lean.

There's no encoding.
There's no primitive.

There's just
the information,
preserved.

---

---
